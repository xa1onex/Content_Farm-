# Отдельный SOCKS5 для каждого эмулятора

Требование: весь внешний трафик Android проходит через закреплённый за экземпляром SOCKS5. Управление ADB/Appium остаётся локальным. При отказе маршрута доступ в интернет закрывается; задания на публикацию не запускаются.

Статус: архитектура выбрана для проверки. Маршрутизация, проверка UDP, блокировка обходных путей и интеграция проверки сети с публикацией **ещё не реализованы и не проверены на ПК**. Диагностика ниже не включает прокси и не подтверждает изоляцию.

## Диагностика перед настройкой

Из каталога проекта в обычном PowerShell:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\check-emulator-network.ps1
```

Скрипт читает адаптеры, IPv4/основные маршруты Windows, сведения о виртуализации, состояния MuMu и доступные мостовые настройки привязанных устройств. Эмуляторы не запускаются; сеть, драйверы и настройки Windows/MuMu не меняются. ADB не вызывается. Логины, пароли, токены и файлы настроек сторонних прокси не запрашиваются. В отчёте есть названия адаптеров и их адреса; его не следует публиковать в Git.

Отчёт сохраняется в `%LOCALAPPDATA%\ShortPost\network-preflight\latest.json` (или соответствующем `state_dir`) и передаётся серверу с обычным токеном Worker. Ключ `network_preflight` находится в текущем heartbeat Worker; следующий heartbeat может его заменить, поэтому оператор должен сохранить полученный отчёт отдельно. Серверные задания и результаты публикаций не создаются.

Для сохранения только на ПК используйте `-LocalOnly`. Для передачи нужен ранее настроенный токен Worker текущего пользователя. Если Worker занят, отчёт сохраняется локально, а отправка останавливается: повторите команду после завершения Worker. Не останавливайте выполняющуюся публикацию ради диагностики.

## Предлагаемая схема

```text
MuMu №0, отдельный внутренний адрес ─┐                    ┌─ SOCKS5 №0
MuMu №1, отдельный внутренний адрес ─┼─ изолированная сеть ─ шлюз
MuMu №2, отдельный внутренний адрес ─┘                    └─ SOCKS5 №1/№2
```

Один шлюз обслуживает все экземпляры и выбирает SOCKS5 по внутреннему адресу/интерфейсу устройства. Кандидат — sing-box на небольшом Linux-шлюзе. Размещение на этом ПК и совместимость виртуализации с MuMu требуется проверить; автоматическая установка Hyper-V/WSL и переключение гипервизора не выполняются. При несовместимости потребуется отдельный шлюз в локальной сети либо другая подтверждённая схема.

Мост MuMu сам по себе не создаёт изоляцию. У эмуляторов не должно оставаться второго NAT-подключения или пути через домашний роутер. Нельзя просто включить мост на физический Ethernet/Wi-Fi и считать задачу решённой. Нужны проверенные правила шлюза/сегмента сети и закрытый прямой выход.

Постоянное соответствие: `external_id → instance_index/Android ID → внутренний адрес → proxy_id → ожидаемый внешний IP`. Секреты вводятся локально и хранятся отдельно от Git и диагностических отчётов. Изменение порта ADB после включения моста требует отдельной проверки привязки и доступности; внешний доступ к ADB/Appium не открывается.

DNS должен обслуживаться через маршрут соответствующего устройства, без общего прямого резолвера. IPv6 либо маршрутизируется тем же способом, либо блокируется. Если SOCKS5 не поддерживает UDP ASSOCIATE/реальную передачу UDP, UDP блокируется без прямого обхода; это ограничение фиксируется в отчёте, а приложения проверяются с TCP. Называть такой режим полной поддержкой всех протоколов нельзя. Проверяется именно SOCKS5 UDP, а не нестандартное UDP-over-TCP, которое провайдер может не поддерживать.

## Проверка перед масштабированием

1. Сохранить исходные настройки и способ восстановления. Поднять шлюз без переключения основной сети Windows.
2. Перевести только MuMu №0 в выделенную сеть; сверить его Android ID и сохранить локальное управление.
3. Подтвердить внешний IP, HTTPS, DNS, поведение UDP и IPv6; открыть новые видео Instagram и Google Play.
4. Отключить прокси, остановить шлюз, перезапустить шлюз и эмулятор: во всех отказах прямой интернет должен оставаться недоступным. Одной проверки IP в браузере недостаточно — нужен контроль трафика на шлюзе/выходе.
5. Подключить второй эмулятор и подтвердить разные выходы, отсутствие смешивания DNS и сохранение привязок после перезапуска.
6. Подключить сетевую проверку Worker перед получением/началом задания; при ошибке приостанавливать работу. После нажатия публикации сбой сети требует проверки результата и не разрешает повторную отправку автоматически.
7. Только после этого переносить настройки на остальные экземпляры и продолжать проверку публикации из Drive.
